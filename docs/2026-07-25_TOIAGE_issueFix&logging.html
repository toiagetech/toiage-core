Payload Logging for Failed Requests — Fixed

Issue

When POST /stories/generate returned a 422 error, the request payload was not captured in the logs. This happened because:

  1. FastAPI’s 422 validation errors occur before the endpoint handler runs, so the handler’s logger.info("Story generation request received", ...) never executes
  2. The ObservabilityMiddleware only logged request metadata (method, path, status) but not the request body

Changes Made

app/utils/observability.py

  • Added _capture_request_body() function that:
    • Reads the request body for POST/PUT/PATCH methods
    • Re-injects the body into the request stream so downstream handlers can still access it
    • Pretty-prints JSON for readability
    • Truncates bodies larger than 4KB to keep logs manageable
  • Updated ObservabilityMiddleware.dispatch() to capture the body before calling the endpoint
  • Updated _log_request() to include request_body in the log extra dict for all requests (especially 4xx/5xx failures and exceptions)

How It Works Now

  1. Request arrives at middleware → body is captured and re-injected
  2. If validation fails (422) → middleware logs the request with the payload as request_body in the log extra fields
  3. If the handler succeeds → middleware logs normally (body also included for 2xx)
  4. If an exception occurs → middleware logs the error with the payload

Where Stories Are Stored in the Backend

Stories are stored in the PostgreSQL database in the stories table.

Database Details

  • Database: PostgreSQL (toiage database)
  • Connection string: postgresql+psycopg://postgres:postgres@localhost:5432/toiage
  • Table: stories
  • ORM: SQLModel (SQLAlchemy-based)

Table Schema (stories)

Column Type Description
id int (PK) Auto-incremented unique ID
title str Generated story title (e.g. “The Glowing Tree Hug”)
content str Full story text (nullable=False)
goal str Learning goal (e.g. “friendship”)
story_mood str Story mood (e.g. “bedtime”)
story_length str Story length (e.g. “short”)
theme str Story theme/setting (e.g. “forest”)
today_context str Optional context about child’s day
age_group str Legacy field
skills str Legacy field
difficulty str Legacy field
created_at datetime When story was created

Storage Flow

  1. Parent clicks “Generate Story” in the UI
  2. Frontend sends POST /stories/generate with childId, goal, storyMood, storyLength, theme
  3. Backend (app/services/stories.py) calls the LLM (OpenRouter → google/gemini-3.5-flash-lite)
  4. LLM returns the story text
  5. Backend parses title + content from the LLM response
  6. Backend saves the story to the stories table via SQLModel: session.add(story) → session.commit()
  7. Story is persisted in PostgreSQL with an auto-generated id and created_at timestamp
  8. API returns the saved story (with id, title, content, provider, model) to the frontend

Story Storage Flow — How It Works

You’re right — there are 40 stories in the DB. Here’s exactly what happens on every POST /stories/generate call:

The Flow (Both Mock & LLM Modes)

Frontend POST /stories/generate
        ↓
Backend calls LLM (mock OR openrouter)
        ↓
LLM returns story text
        ↓
Backend parses title + content
        ↓
Backend SAVES to DB  ← session.add(story) + session.commit()
        ↓
Backend returns the SAVED DB row (with id, created_at)
        ↓
Frontend receives story

Key Point

The story is ALWAYS returned from the DB row, not directly from the LLM.

Even though the content comes from the LLM (mock = static, openrouter = real AI), the backend persists it to the stories table first, then returns the saved row. That’s why every call creates a new DB record — 40 calls = 40 rows.

Code Path (app/services/stories.py lines 211-224)

# 6 — persist
story = Story(
    title=title,
    content=content,
    goal=body.goal,
    story_mood=body.story_mood,
    story_length=body.story_length,
    theme=body.theme,
    today_context=body.today_context,
)
session.add(story)      # ← adds to DB
session.commit()        # ← saves to DB
session.refresh(story)  # ← gets id + created_at

Then the API returns story.id, story.title, story.content, story.created_at — all from the saved DB row.

Why So Many Stories?

Every generate call = 1 new row. There’s no deduplication or retrieval — each call is treated as a new story generation event. The DB grows by 1 row per call.

Do You Want to Change This?

Options:

  1. Keep as-is — every generation is a new story record (current behavior, good for history/analytics)
  2. Don’t persist — return the LLM response directly without saving to DB (good for “preview before saving”)
  3. Add a GET endpoint — GET /stories to list/retrieve saved stories (so the DB is useful)
  4. Add cleanup — delete old stories or limit how many are stored

How It Works

      ↓

      ↓ Yes
Query DB for matching story:
  WHERE goal = "friendship"
    AND theme = "forest"
    AND story_mood = "bedtime" (if provided)
    AND story_length = "short" (if provided)

      ↓

      ↓ No
Fall back to LLM_PROVIDER (openrouter/mock) → call LLM → save new row
